### 关键规则

#### 评分原则

- 你的判断必须基于 sessions.json 和 workspace 中的**具体交付件**，而非假设
- 你**只需判断叶子节点**，AND/OR 组合结果会自动派生
- 如果 Agent 的输出部分正确，应如实判断每个叶子节点的通过/未通过
- 必须覆盖所有叶子节点，遗漏的节点将被视为未通过

#### 特殊情形判据

- 如果任务涉及搜索/浏览获取外部信息，务必严格按照下述**搜索信息忠实判据**小节的规程执行，判断 Agent 是否从搜索结果中正确提取并忠实使用信息，未发生编造/误用/幻觉/替换。
- 如果Rubric叶子假设了某种情况，按下面逻辑处理：
  - 如果该叶子节点在OR组中或者该假设情况属于完成任务的必要环节，按实际情况判断是否通过，不可按照下面两种情况推断。
  - 如果该叶子节点假设的情况不属于完成任务必须的环节，且**确实**在实际执行过程中没有出现（能从执行轨迹或工作区明确确认该前提未出现），标记为通过，并在 reasoning 中说明该假设情况未涉及，且不影响任务完成，推定为通过。
  - 如果**无法确认**该叶子节点的假设情况是否被触发，或证据不足以判断其是否达成，应将其标记为未通过，并在 reasoning 中说明证据不足
- 如果任务涉及"最新"、"前N天"、"下周N"等时间推理以及其他有明确时效、时间窗口类的要求，务必严格按照下述**时间窗口判据**小节的规程执行。

#### 时间窗口判据（强制规程）

涉时语义清单：
- **相对时间**：`最新` / `最近N天` / `最近一周` / `前N天` / `过去N天` / `上N天` / `后N天` / `未来N天` / `下周N` / `本周` / `本月` / `上月` / `今年` 等
- **绝对时间**：指定日期、指定日期范围（如"7月1日—7月3日"）

凡涉及上述语义的叶子节点（无论完成叶还是质量叶），在给出 `passed` 之前**必须**完成以下步骤：

1. **锚定执行日期**：取 user prompt「## 执行轨迹元信息」段中的执行日期（UTC+8，权威基准）。**禁止**使用 Agent 自述的"今天"、当前评测时间、工具返回内容里出现的日期作为基准。
2. **换算绝对窗口**：按方向约定将涉时要求换算成绝对日期区间。换算时必须使用Linux系统自带的date工具或者使用python脚本，不得自行推理，防止时间推理错误。
   - `前/上/过去` = 早于执行日；`后/未来/下` = 晚于执行日。
   - 示例（执行日 = 2026-07-04）：
     - `最近一周` = [2026-06-27, 2026-07-04]
     - `未来3天` = [2026-07-04, 2026-07-07]
     - `前三天` = [2026-07-01, 2026-07-03]
3. **找 Agent 实际日期**：从工具调用关键词、抓取 URL 中的日期片段（如 `t20250414`、`depdate=2026-07-05`）、交付物正文中定位 Agent 实际使用/产出的日期。
4. **比对并定论**：只有Agent交付内容的实际日期**完全覆盖**所需窗口才视为满足；只要交付内容未能完全覆盖窗口，相关叶子**直接判未通过**，`reasoning` 写"时间窗口不满足：要求 [窗口]，Agent 实际 [实际日期]"。
5. **禁止重新解释**：时间窗口满足是**完成叶**和**质量叶**的硬性闸门，即便 Agent 抓取/总结了内容，只要时间不符，相关叶子一律未通过，不得重新解释或弱化影响。
6. **证据不足**：若无法确认 Agent 实际日期，按既有"证据不足"规则判未通过，`reasoning` 注明"无法确认时间窗口是否满足"。
7. **写入 `time_analysis`**：在逐叶评分过程中将以上分析（执行日期、各涉时叶子 id 及所需窗口、Agent 实际日期、逐项满足/不满足结论）写入 `time_analysis` 字段；无时间要求则写"无时间窗口要求"。

#### 搜索信息忠实判据（强制规程）

适用范围：当任务要求 Agent 通过搜索/浏览类工具（如 web_search、web_fetch、browse、browser 等）获取外部信息，并将所得信息用于交付物时，本规程强制适用。信息来源包括但不限于：网络检索结果、抓取网页正文、API 返回结构化数据中由搜索/浏览得到的字段。

凡其所需信息来源于搜索/浏览结果的叶子节点（无论完成叶还是质量叶），在给出 `passed` 之前**必须**完成以下步骤：

1. **识别涉搜叶子**：逐叶判定该叶子所要求的信息是否需从搜索/浏览结果获取（信息无法仅凭任务输入件或 Agent 内部知识得出，须依赖外部检索）。列出所有涉搜叶子 id。
2. **定位搜索返回内容**：从 user prompt「## 执行轨迹元信息」段的工具调用序列中找到搜索/浏览类工具调用（带 `query` 行的工具，包括直接搜索工具如 `web_search`/`web_fetch`/`browser`，以及通过 `exec` 调用搜索类 skill 脚本的间接搜索调用），并在 `sessions.json` 中查阅对应工具返回的原始内容（搜索结果摘要、抓取网页正文、API 响应等）。**只采信工具实际返回的内容**作为比对基准；不得使用 Agent 自述或后续转述。
3. **比对交付物与返回内容**：将 Agent 最终交付物中对应涉搜叶子的信息，与第 2 步定位的搜索返回内容逐项比对，检测以下任一情形：
   - **编造/幻觉**：交付物中出现搜索返回内容中不存在的信息（凭空捏造的评分、数字、名称、日期等）。
   - **误用/错配**：将搜索返回的内容用于错误对象（如把电影 A 的评分安到电影 B 上）、张冠李戴、字段错位。
   - **替换/篡改**：用非搜索来源的内容替换本应来自搜索结果的信息，或在未重新搜索的情况下用旧/无关数据顶替。
   - **断章取义**：抽取搜索返回内容片段时改变其原意，导致与用例要求的信息不符。
4. **定论并标记**：只要发现上述任一情形，相关涉搜叶子**直接判未通过**，`reasoning` 写"搜索信息提取不忠实：要求 [所需信息]，搜索返回 [实际返回内容]，Agent 交付 [交付内容]，存在 [编造/误用/替换/断章取义]"。
5. **禁止重新解释（硬性闸门）**：搜索信息的忠实提取与使用是**完成叶**和**质量叶**的硬性闸门，即便交付物在形式上满足了叶子措辞（如格式、条数、字段齐全），只要存在编造/误用/幻觉/替换，相关叶子一律未通过，不得重新解释或弱化影响。
6. **证据不足**：若无法确认搜索返回内容（如工具调用失败、返回为空、sessions.json 缺失对应记录），按既有"证据不足"规则判未通过，`reasoning` 注明"无法确认搜索信息是否被忠实提取"。此条针对"无法核实"，与第 4 条"已核实存在不忠实"区分。
7. **写入 `info_fidelity_analysis`**：在逐叶评分过程中将以上分析即时记录（不得事后倒填）到 `info_fidelity_analysis` 字段，须包含：涉搜叶子 id 及其所需信息、对应搜索工具调用及返回内容摘要、Agent 交付内容、逐项忠实/不忠实结论；任务不涉及任何搜索/浏览获取外部信息时，写"无搜索信息忠实性要求"。

#### 输出规范

- 每个叶子节点的 reasoning 应引用你观察到的**具体事实**（如"Agent 在第 3 轮对话中成功创建了日历事件"），而非泛泛而谈
- confidence 反映的是**你对评估结果整体的把握程度**，而非任务完成质量
- 每个叶子节点 id 已在 Rubric 树中方括号中标注（如 `[node-xxxxxxxxxxxx]`），输出 rubric_results 时使用这些 id 作为键
