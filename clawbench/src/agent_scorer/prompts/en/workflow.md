### Evaluation Workflow

1. **Read the task configuration**: Inspect the task directory to understand the task requirements and input files, if any.
2. **Read the execution trajectory**: Read `sessions.json` in the result directory (the "Execution Trace Metadata" section of the user prompt provides the execution date and tool-call sequence) to understand what the agent did.
3. **Inspect the workspace**: Examine the files in `workspace/` under the result directory to verify the outputs; for different deliverable types, select the appropriate inspection method according to the "Deliverable Inspection Protocol" below.
4. **Score each leaf**: For every rubric leaf node, determine pass/fail based on evidence and provide a concrete justification.
   - If a leaf involves a recency/time-window requirement (such as latest, previous N days, next N days, the past week, etc.), first apply "Critical Rules → Time-Window Criterion" to anchor the execution date, convert the required window, and verify the dates actually used by the agent before judging `passed`, and record this analysis in the `time_analysis` field. If the time window is not satisfied, mark the leaf as failed; do not weaken the conclusion after the fact. If the task has no time requirement, write "No time-window requirement" in `time_analysis`.
   - If the information required by a leaf comes from search/browsing results, first apply "Critical Rules → Search-Information Fidelity Criterion" to locate the search returns and compare whether the agent's deliverable extracted them faithfully (no fabrication/misuse/hallucination/substitution), then record this analysis in the `info_fidelity_analysis` field. If the extraction is unfaithful, mark the leaf as failed; do not weaken the conclusion after the fact. If the task does not involve obtaining external information through search/browsing, write "No search-information fidelity requirement" in `info_fidelity_analysis`.
5. **Assign confidence**: Indicate how confident you are in the overall scoring result.
6. **Assess uncertainty and anomalies**: Determine whether this scoring requires human review (uncertainty), and provide the structured `needs_human_review` and `review_notes`. Set `needs_human_review=true` if any of the following occurs, and specify the matched condition and its basis in `review_notes`:
   - **Scoring-process anomaly**: An anomaly occurs during evaluation, or `sessions.json`/`workspace` etc. are missing, so that scoring cannot be completed fully according to the protocol;
   - **Problem with the tested model's execution environment**: A container/service anomaly, critical tools being unavailable, or the environment not matching the task requirements, which affects your judgment of the deliverable;
   - **The query conflicts with the actual circumstances / insufficient information / contradiction**: The task requirements do not match the actual situation the agent was in, making a definitive judgment difficult;
   - **Low confidence in the evaluation**: Ambiguous evidence, boundary cases, low confidence, etc., when you are unsure about some judgments.
   - If none of the above applies, set `needs_human_review=false` and write "No anomalies" in `review_notes`.
   Note: regardless of whether human review is needed, any anomaly during scoring (such as a failed tool call) must be documented by creating `exceptions.md` under the `verifier/judge/` folder in the result directory.
7. **Organize evidence**: If key evaluation evidence was generated (e.g., webpage screenshots), create a `proof` folder under `verifier/judge/` in the result directory and store the evaluation evidence there.
8. **Clean up temporary files**: Clean up temporary scripts and files (not evidence) generated during the evaluation, but do not delete any original files or environment dependencies (e.g., the Chromium executable required by Playwright)!
